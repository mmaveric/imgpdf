# Design: update-spec-browser-risks

## Context

SPEC.md v2.0 перенёс всю обработку в браузер, но четыре свойства браузерной платформы остались незафиксированными: доступность `OffscreenCanvas` в Safari, зависимость пика памяти от настроек DPI/качества, надёжность `<a download>` для больших Blob на iOS и поздняя/кривая поддержка `imageOrientation` в Safari. Кода ещё нет — изменения касаются только SPEC.md и OpenSpec-спек, поэтому цена решения сейчас минимальна, а посреди этапов 3–4 — высока.

## Goals / Non-Goals

**Goals:**

- Зафиксировать минимальную поддерживаемую версию iOS Safari и поведение на неподдерживаемых браузерах.
- Описать бюджет памяти генерации как функцию настроек (страницы × DPI × качество) и ввести кап DPI на мобильных.
- Определить механизм доставки готового PDF с fallback через Web Share API.
- Перенести верификацию EXIF-ориентации на реальном iPhone с этапа 6 на этап 3.

**Non-Goals:**

- Fallback-ветка пайплайна для Safari < 16.4 (resize в главном потоке) — осознанно не делаем.
- Прогноз размера PDF в UI до генерации — рассмотрено, отложено в бэклог (см. Decisions).
- Любые изменения кода — кода в проекте нет.

## Decisions

### D1. Минимум iOS Safari 16.4, без fallback

`OffscreenCanvas` с 2D-контекстом — Safari 16.4+ (март 2023). Альтернатива — fallback-ветка: resize/encode на обычном Canvas в главном потоке, в воркер уходят только готовые JPEG-байты для `embedJpg`. Это удваивает код пайплайна и матрицу тестирования ради iOS, которым к моменту релиза 3+ года. Решение: **жёсткий минимум 16.4**. На браузере без `OffscreenCanvas` (feature-detect при старте) приложение показывает явное сообщение «браузер не поддерживается», а не ломается молча на генерации.

### D2. Кап DPI 200 на мобильных, формула бюджета в спеке

Пик памяти ≈ Σ(JPEG-байты страниц) × 2 в момент `pdfDoc.save()`. При 200 страницах: 150 DPI → пик ~250–350 МБ (выживаемо), 300 DPI → ~1–1.5 ГБ (смерть вкладки на телефоне). Решение: на мобильных устройствах эффективный DPI ограничивается **200** (A4 @ 200 DPI ≈ 3.9 МП/стр — для фото достаточно). Детект — `navigator.userAgentData.mobile` с fallback на UA-строку; грубость детекта приемлема, кап мягкий по последствиям (чуть ниже качество, а не отказ). Альтернатива — прогноз размера PDF в UI перед генерацией: полезно, но это новая UI-фича, не правка рисков → бэклог §4.

### D3. Доставка PDF: download + Web Share API

Первичный путь — `<a download>` c blob URL, как в спеке. На устройствах, где `navigator.canShare({files: [pdf]})` истинно (iOS 15+, Android Chrome), дополнительно показывается кнопка «Поделиться» → системный share sheet (оттуда доступно «Сохранить в Файлы»). Это страхует известную ненадёжность download-атрибута с большими Blob на iOS и нативнее для телефона. Не замена, а дополнение: download остаётся для десктопа.

### D4. EXIF-верификация — в DoD этапа 3

`createImageBitmap(file, {imageOrientation: 'from-image'})` в Safari поддержан поздно; молчаливая деградация здесь — перевёрнутые страницы в готовом PDF. Обнаружить это на этапе 6 = переделывать этап 3. Решение: DoD этапа 3 дополняется пунктом «портретное фото с iPhone отображается в правильной ориентации в реальном Safari iOS» (через LAN-доступ; допустимо временно поднять любой статик-сервер до этапа 5).

## Risks / Trade-offs

- [Кап 200 DPI режет качество для сценария «скан документа» на телефоне] → для фото-контента 200 DPI достаточно; если появится реальный запрос — прогноз размера из бэклога снимет необходимость капа.
- [UA-детект мобильных ненадёжен (iPad с desktop-UA и т.п.)] → последствие ошибки мягкое: iPad получит кап (качество чуть ниже) или его не получит (памяти у iPad хватает). Не блокер.
- [Минимум 16.4 отсекает старые устройства] → сообщение о неподдерживаемом браузере честнее молчаливой поломки; доля iOS <16.4 к 2026 мала.
- [Web Share требует user gesture и может отклоняться] → download-ссылка всегда остаётся рядом как основной путь.

## Open Questions
