# imgpdf — спецификация проекта

Версия: 2.1 · 2026-07-17 · Статус: архитектурный пивот, готово к реализации.

**Что изменилось с v2.0:** зафиксированы браузерные границы: минимум iOS Safari 16.4 (OffscreenCanvas), кап DPI 200 на мобильных (бюджет памяти генерации), Web Share fallback для скачивания на iOS, тест EXIF-ориентации перенесён в DoD этапа 3.

**Что изменилось с v1.0:** вся обработка изображений и сборка PDF переехала в браузер (Canvas + `pdf-lib`). Go больше не содержит бизнес-логики — это тонкий статический файл-сервер для LAN-доступа. Раздел «дизайн» закрыт: интерактивный прототип уже собран и служит основой для `web/`.

## 1. Что это

Локальный веб-инструмент: набор фото → PDF. Открывается с десктопа и с телефона через браузер в локальной сети. Вся обработка — decode, поворот, ресайз, сборка PDF — происходит **в браузере**, ничего не загружается на сервер. Go-бинарник нужен только чтобы раздать статику по LAN одной командой.

## 2. Зафиксированные решения

| Область | Решение | Обоснование |
|---|---|---|
| Раздача | Go, `embed.FS` + `http.FileServer`, без единого API-роута | вся логика клиентская, серверу нечего обслуживать кроме файлов |
| Обработка изображений | `createImageBitmap` + Canvas 2D в браузере | decode/поворот/ресайз — нативные возможности браузера, EXIF-ориентация учитывается автоматически |
| Сборка PDF | `pdf-lib` (vendored, без CDN) | pure JS, работает в Web Worker, произвольный размер страниц |
| Параллелизм генерации | Web Worker | тяжёлый цикл не должен блокировать UI/анимацию прогресса |
| HEIC/HEIF | **не поддерживается в MVP**, полагаемся на автоконверт iOS в JPEG при выборе через file input | WASM-декодер (`libheif-js`, ~1–2 МБ) — решение отложено на v1.1, если понадобится |
| Сессии/сервер-side state | **отсутствуют** | состояние живёт в памяти вкладки браузера; изоляция между устройствами — бесплатно |
| Фронтенд | Vanilla JS + Alpine.js + SortableJS, без сборки | без изменений от v1.0, прототип уже реализует этот слой |
| Формат страницы/поля/fit-fill/качество | без изменений от v1.0 | это параметры бюджета памяти: страницы × DPI × качество определяют пик потребления при генерации (см. §6.3), а не только вид PDF |
| Минимальная платформа | iOS Safari 16.4+, актуальные Chrome/Firefox/Safari десктоп и Chrome Android; без fallback-ветки | `OffscreenCanvas` с 2D-контекстом появился в Safari 16.4; fallback (resize в главном потоке) удваивает код пайплайна ради устройств 3+ лет |
| Multi-device continuity | вне скоупа, теперь принципиально (не просто «отложено») | без сервера нет общего состояния между устройствами; если понадобится — это уже отдельный бэкенд |

### 2.1 Зависимости

**JS (vendored в `web/vendor/`, без CDN — офлайн-LAN инструмент не должен зависеть от сети):**

- `alpine.esm.js` — реактивность UI
- `sortable.min.js` — drag-reorder
- `pdf-lib.min.js` (~700 КБ) — сборка PDF

**Go (стандартная библиотека, без внешних зависимостей):**

- `embed`, `net/http`, `net` (для перечисления LAN-адресов)
- опционально `github.com/skip2/go-qrcode` — печать QR в терминал (см. §5.3); раньше не помещалось в MVP по бюджету сложности, теперь помещается почти бесплатно

Важно: зависимость от `libvips`/`heif-convert` на хосте **полностью исчезает** — раньше это было единственное, что ломало «чистую» кросс-компиляцию; теперь бинарник компилируется куда угодно без CGo и без внешних тулов.

## 3. Функциональные требования (MVP)

Без изменений от v1.0 (§3), кроме удаления пунктов про мультисессионность:

1. Загрузка с десктопа (drag&drop + клик) и с мобильного (камера/галерея).
2. Очередь загрузки с прогрессом по файлу — теперь это реальный прогресс обработки (decode → resize → thumbnail), не сетевой.
3. Сетка миниатюр в текущем порядке, drag-reorder (мышь и тач).
4. Поворот на 90°, применяется как трансформация Canvas при генерации.
5. Удаление отдельного изображения и всей очереди.
6. Настройки PDF: формат страницы, ориентация, поля, fit/fill, качество JPEG, имя файла.
7. Генерация с реальным прогрессом «n из m» (Web Worker шлёт сообщения по мере обработки каждой страницы), автоскачивание по завершении.
8. При старте бинарник печатает в консоль LAN-адреса (и опционально ASCII QR-код).

~~Мультисессионность и TTL-очистка~~ — не нужны, состояние не покидает вкладку.

## 4. Вне скоупа MVP → бэклог

QR-код в UI (терминальный есть в MVP) · сетки N×M на страницу · «режим сканера» · crop · HEIC WASM-декодер · PWA/офлайн-кеш (service worker) · целевой размер файла · прогноз размера PDF в UI до генерации · тёмная тема · синхронизация между устройствами (требует отдельного бэкенда — сознательно вне направления этого проекта).

## 5. Архитектура

### 5.1 Структура проекта

```
cmd/imgpdf/main.go     флаги, embed, LAN-адреса, опционально QR
web/
  index.html            разметка (основа — prototype.html)
  app.js                Alpine store: UI-состояние, reorder, rotate, settings
  pipeline.js           ingest → normalize → thumbnail (главный поток)
  pdf-worker.js         Web Worker: resize → pdf-lib → Blob
  pipeline-math.js       чистые функции: fit/fill, page-size↔DPI, sanitizeFilename, sniffFormat
  styles.css
  vendor/
    alpine.esm.js
    sortable.min.js
    pdf-lib.min.js
```

Заметь: `internal/session`, `internal/imaging`, `internal/pdf`, `internal/heic` из v1.0 — все исчезли. Go-часть — это буквально один файл.

### 5.2 main.go — обязанности

- Флаги: `--host 0.0.0.0`, `--port 8080`, `--dev` (отдавать `web/` с диска вместо `embed.FS`, для живой правки без пересборки).
- `http.FileServer` поверх `embed.FS`; `Cache-Control: no-cache` для `index.html`, `max-age` для версионированных `vendor/*` (они не меняются между релизами).
- При старте — перечислить интерфейсы (`net.Interfaces()`), напечатать все LAN-адреса вида `http://192.168.x.x:8080`.
- `/healthz` — `200 OK`, для быстрой проверки, что процесс жив.
- Graceful shutdown по `SIGINT/SIGTERM`.

Это всё. Никаких `/api/*` роутов не существует в этой архитектуре.

### 5.3 Опциональный терминальный QR (нижняя граница v1.1, но дёшево — можно сразу)

При старте, рядом с адресом, печатать ASCII-QR через `go-qrcode` (`qrcode.New(url, qrcode.Medium)` → `.ToString(false)`). Сканить телефоном прямо из терминала — экономит набор IP руками.

## 6. Клиентский пайплайн (замена серверных §6–7 из v1.0)

### 6.1 Приём файла (`pipeline.js`, главный поток)

При старте приложения — feature-detect `OffscreenCanvas`: отсутствует → полноэкранное сообщение «браузер не поддерживается, нужен iOS 16.4+ / актуальный браузер», UI загрузки недоступен.

1. `file.type` + сниф первых байт (сигнатуры JPEG/PNG/WebP; для ISOBMFF-контейнеров — брейнды `heic/heix/hevc/mif1` → детект HEIC).
2. HEIC определён → карточка сразу уходит в состояние ошибки: «HEIC не поддерживается — на iPhone включите передачу «Автоматически», это сконвертирует в JPEG». Дальше файл не обрабатывается.
3. `createImageBitmap(file, { imageOrientation: 'from-image' })` — decode с явным учётом EXIF-ориентации (опция задаётся явно, а не полагается на дефолт браузера — он исторически отличался между Chrome/Safari/Firefox).
4. Отрисовать на thumbnail-canvas (длинная сторона 320px) → `toBlob('image/jpeg', 0.8)` → `URL.createObjectURL` для превью в сетке.
5. Оригинальный `ImageBitmap` (или сам `File`, если экономим память — decode по требованию на этапе генерации) кладётся в массив `images` вместе с метаданными: id, name, width, height, rotation=0, uploading, progress.
6. При удалении карточки — `URL.revokeObjectURL` на её thumbnail, иначе течёт память на больших очередях.

### 6.2 Генерация PDF (`pdf-worker.js`, Web Worker)

Зачем воркер: цикл resize+encode+embed для 50–200 изображений на слабом телефоне может занять секунды и заблокировать главный поток — анимация прогресса (тот самый scan-beam из прототипа) должна оставаться живой, поэтому вся тяжёлая часть уезжает в воркер, а главный поток только рисует прогресс по сообщениям `postMessage({done, total})`.

Для каждого изображения по порядку **в воркере**:

1. Взять исходное изображение (передано как `Blob`/`ImageBitmap` — `ImageBitmap` можно передавать в воркер как Transferable без копирования).
2. `OffscreenCanvas` — применить пользовательский `rotation`, отрисовать в целевом размере (см. математику fit/fill/DPI — идентична v1.0 §7, просто теперь на JS в `pipeline-math.js`, а не на Go). Эффективный DPI на мобильных (детект `navigator.userAgentData.mobile`, fallback — UA-строка) ограничен 200 — кап бюджета памяти, см. §6.3.
3. `convertToBlob({type:'image/jpeg', quality})`.
4. `pdfDoc.embedJpg(bytes)` + `page.drawImage(...)` через `pdf-lib`.
5. `postMessage({done: i+1, total})` — главный поток обновляет счётчик и progress-ring в реальном времени (не симуляция, как в прототипе, а настоящий прогресс).
6. По завершении всех страниц — `pdfDoc.save()` → `Uint8Array` → обратно в главный поток → `Blob('application/pdf')` → `<a download>`. Если `navigator.canShare({files})` истинен для PDF-файла (iOS 15+, Android Chrome) — рядом со ссылкой скачивания показывается кнопка «Поделиться» (Web Share API, системный share sheet): страховка от ненадёжности `download`-атрибута с большими Blob на iOS.

Санитайзер имени файла — та же whitelist-логика, что и в v1.0 (`[a-zA-Z0-9._ -]`), теперь просто чистая JS-функция в `pipeline-math.js`.

### 6.3 Границы памяти

- Обрабатывать изображения **последовательно**, не декодировать все 200 сразу — держать в памяти оригинал текущего + миниатюры остальных.
- Пик памяти генерации ≈ Σ(JPEG-байты всех страниц) × 2 в момент `pdfDoc.save()` (полная сериализация документа). Ориентиры для 200 страниц A4: 150 DPI (~300–600 КБ/стр) → пик ~250–350 МБ — выживаемо на телефоне; 300 DPI (~1.5–2.5 МБ/стр) → пик ~1–1.5 ГБ — смерть вкладки. Отсюда кап DPI 200 на мобильных (§6.2 п.2).
- Canvas/OffscreenCanvas имеют практические лимиты по размеру на мобильных браузерах (особенно старый iOS Safari) — если исходное фото больше ~24 МП, стоит предварительно ужать перед основной обработкой.
- Мягкие лимиты в UI (по умолчанию 200 файлов, предупреждение выше ~80–100) — не серверная защита, а просто разумная подсказка пользователю, реальный потолок — память устройства.

## 7. Фронтенд (UI-слой)

Без изменений от v1.0 §8 — прототип (`prototype.html`) уже реализует Alpine store, состояния empty/grid/settings/result, реальный drag-reorder через SortableJS, оптимистичный поворот. Единственное отличие: `addMock()` в прототипе заменяется на реальный вызов `pipeline.js` при подключении настоящих файлов, а симулированный прогресс генерации (`setTimeout`-цепочка) — на реальные сообщения от `pdf-worker.js`.

## 8. Дизайн — статус

Закрыт. `prototype.html` — рабочий кликабельный прототип (концепция «сканер + контактный лист», токены, все 4 состояния, переключатель телефон/десктоп для ревью). Он же становится каркасом `web/index.html` + `web/styles.css` на этапе 3.

## 9. Нефункциональные требования

- Браузерная поддержка: актуальные Chrome/Safari/Firefox на десктопе, Safari iOS и Chrome Android на мобильных — целевая матрица для ручного QA.
- Память: пиковое потребление ≈ (МП текущего изображения × 4 байта) × 2 (thumbnail + full-res), плюс буфер `pdf-lib` для уже собранных страниц — растёт линейно с числом страниц (формула и ориентиры — §6.3; кап DPI на мобильных — §6.2), проверить верхнюю границу на реальном телефоне при 150–200 страницах.
- Ориентир скорости: 30 фото по 12 МП → PDF, воркер не должен давать ощутимый фриз UI независимо от итогового времени.
- Graceful shutdown Go-процесса; `/healthz`.
- Безопасность: раз обработка локальная и без сети — модель угроз для доверенной LAN практически исчезает (не считая самого факта, что сервер слушает `0.0.0.0` без авторизации, как и раньше).

## 10. Подводные камни

- **iOS Safari HEIC**: режим передачи «Оригиналы» пришлёт настоящий HEIC → ошибка по плану §6.1. Тестировать в обоих режимах на реальном iPhone.
- **`imageOrientation` по умолчанию** отличается между браузерами исторически — задавать явно `'from-image'`, не полагаться на дефолт.
- **Лимиты Canvas на мобильном Safari**: не только общий размер, но и суммарная память всех живых canvas-контекстов — держать активными как можно меньше одновременно, `OffscreenCanvas` явно закрывать/обнулять после использования.
- **`URL.createObjectURL` без `revokeObjectURL`** — классическая утечка памяти на длинных сессиях с частым добавлением/удалением карточек.
- **Web Worker + `pdf-lib`**: библиотека должна быть чистым JS без обращений к `window`/DOM — проверить на этапе интеграции, что vendored сборка `pdf-lib` действительно worker-safe (обычно да, но версию стоит закрепить и протестировать явно).
- **Скачивание на iOS Safari**: исторически были нюансы с `download`-атрибутом и большими Blob — протестировать на реальном PDF в 150+ страниц; страховка — кнопка «Поделиться» через Web Share API (§6.2 п.6). Web Share требует user gesture и может быть отклонён пользователем — download-ссылка всегда остаётся рядом.
- **OffscreenCanvas — только с Safari 16.4**: на более старых iOS воркер-пайплайн (§6.2) не работает вообще — отсюда жёсткий минимум платформы (§2) и feature-detect при старте (§6.1).
- SortableJS + touch без `delay` перехватывает скролл — это уже решено в прототипе (`delayOnTouchOnly:true, delay:150`), просто не потерять при переносе в `app.js`.

## 11. Тестирование

- **Чистые функции** (`pipeline-math.js`: fit/fill-математика, page-size↔DPI, sanitizeFilename, sniffFormat) — юнит-тесты через встроенный `node --test`, без лишних зависимостей.
- **Ручная матрица** — обязательна и важнее, чем раньше, раз вся логика теперь в браузере: iPhone Safari (оба режима HEIC-передачи) · Android Chrome · Firefox/Chrome desktop; отдельно — очередь из 150–200 реальных фото на слабом Android для проверки памяти и скорости воркера.
- E2E (Playwright headless) — по желанию, v1.1: клик по полному флоу от загрузки до скачанного PDF-блоба. Не блокирует MVP.

## 12. План реализации

| Этап | Содержание | DoD |
|---|---|---|
| 1. Дизайн | ✅ готово — `prototype.html` | — |
| 2. Чистые функции | `pipeline-math.js`: fit/fill, page-size/DPI, sanitizer, sniff | `node --test` зелёный |
| 3. Canvas-пайплайн | `pipeline.js`: реальный `createImageBitmap` → thumbnail → rotation вместо `addMock()` в прототипе | реальные фото проходят через UI прототипа корректно, поворот совпадает с EXIF; портретное фото с iPhone (EXIF ≠ 1) — в правильной ориентации на реальном iOS Safari |
| 4. PDF + Worker | `pdf-worker.js`, интеграция `pdf-lib`, реальный прогресс вместо `setTimeout`-симуляции | генерация даёт валидный скачиваемый PDF, счётчик отражает реальный прогресс |
| 5. Go static server | `main.go`: embed, LAN-адреса, `--dev`, опционально QR | открывается с телефона по LAN-адресу |
| 6. Полировка | error-состояния (HEIC, повреждённый файл, лимиты), память/revoke, README, Makefile (кросс-компиляция без CGo — теперь тривиальна) | ручная матрица §11 пройдена |

Этапы 2–4 не требуют Go вообще — можно вести разработку и тестировать прямо в браузере (`--dev` или просто открыв `index.html`), Go подключается последним, на этапе 5.

## 13. Открытые мелочи

- HEIC WASM-декодер — осознанно отложен (см. §2, дефолт по умолчанию: не поддерживаем в MVP). Если окажется, что доля HEIC-загрузок высокая — добавить `libheif-js` в v1.1, план не меняется, просто ещё один шаг в §6.1.
- Терминальный QR — решил включить сразу в MVP (§5.3), раз бюджет сложности освободился; если не понравится — выкинуть одной строкой.
- PWA/офлайн-кеш — естественный следующий шаг поверх этой архитектуры, не включён в MVP.
